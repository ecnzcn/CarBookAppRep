# CarBook — Data Model

All entities live in IndexedDB via Dexie (`src/db/db.ts`), one table per
entity, primary key `id` (a `crypto.randomUUID()` string generated by the
owning service). Types are defined once in `src/db/types.ts` and shared by
every layer.

## Maintenance

Covers maintenance, repairs, service entries, and inspections (HU/AU) — one
`type` field distinguishes them so the timeline can render them
distinctly while sharing one form/table.

| Field | Type | Notes |
|---|---|---|
| id, vehicleId | string | |
| date | string | ISO date, when it was done |
| mileage | number | odometer reading at the time |
| type | enum | maintenance / repair / service / inspection |
| title | string | required |
| description, workshop, notes | string? | |
| cost | number? | |
| nextMileage | number? | next due odometer reading |
| nextDate | string? | next due date |
| createdAt, updatedAt | string | |

**Due state** (`services/maintenanceStatus.ts`) compares `nextMileage`/`nextDate`
against the vehicle's current mileage and today's date. When both are set,
the more urgent of the two — mileage or date — decides the status
(`ok` / `dueSoon` / `overdue`), per "the first reached condition determines
the due state."

## FuelEntry

| Field | Type | Notes |
|---|---|---|
| id, vehicleId | string | |
| date | string | ISO date |
| mileage | number | odometer at fill-up |
| liters, pricePerLiter, totalCost | number | |
| station, notes | string? | |

**Consumption** (`services/fuelService.ts`) assumes every fill-up tops off
the tank: consumption for a fill-up is `liters / (mileage - previousMileage)
* 100`. It is only computed between two consecutive entries that both have
a mileage reading — with fewer than two readings, no figure is shown
(never invented).

## Document

| Field | Type | Notes |
|---|---|---|
| id, vehicleId | string | |
| maintenanceId, issueId | string? | at most one is set — a document belongs to a maintenance entry or an issue, or neither (general vehicle document) |
| filename, mimeType | string | |
| createdAt | string | |
| blob | Blob | stored directly in IndexedDB; never leaves the device |

In v1.0 the UI only ever creates a document attached to a maintenance
entry or an issue (via `DocumentAttachments`, used in both of their
forms); a document with neither set is a valid record the type allows but
nothing in the UI produces one. In a backup zip, each document's blob is
written under `photos/` (image mime types) or `documents/` (everything
else) — see [ROADMAP.md](./ROADMAP.md) for why there's no separate photo
entity.

## Relationships

```
Vehicle 1—* Maintenance
Vehicle 1—* Issue
Vehicle 1—* FuelEntry
Vehicle 1—* TireSet 1—* TireEvent
Vehicle 1—* Document (optionally *—1 Maintenance, *—1 Issue)
Vehicle 1—* Reminder
```

Nothing is ever shared across vehicles; every record traces back to exactly
one `vehicleId` (documents indirectly, via their vehicleId field).
